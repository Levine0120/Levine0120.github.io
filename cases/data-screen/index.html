01

TYPE 1 · 一图成屏

一台设备，一张好图。

用三维软件把设备渲染成图，放在屏幕中间，两侧排数据。

  • 单台设备
  • 单个工位
  • 展厅演示
  • 约 1–2 周

一图成屏 · 01

版式：设备在中间，数据围一圈。

设备是视觉中心，数据按「实时 → 统计 → 趋势」分区排开。

运行数据关键指标设备渲染图能耗时间趋势
  1. 拿资料设备照片、图纸、厂家模型
  2. 建模有厂家模型就简化，没有就自己建C4D · Blender
  3. 调材质灯光白色机身 + 品牌色，干净的棚拍光C4D
  4. 选角度出图3/4 侧视，透明底 PNG，按屏幕分辨率
  5. 排数据和动效两侧面板、数值滚动、状态呼吸灯Figma

一图成屏 · 02

同一套版式，换设备就能用。

协作焊接、柔性焊接、模拟产线，共用一套面板和配色。

一图成屏 · 03

交给开发：图是图，数据是数据。

设计交付透明底设备图、面板切图、标注稿
开发实现网页搭面板，图表用 ECharts 一类图表库
数据接口定时刷新数值，状态改颜色

好处

  • 出效果最快，画面最精致
  • 对大屏主机几乎没有要求
  • 换一台设备，只换中间那张图

局限

  • 视角固定，不能转
  • 设备状态只能靠面板表达
  • 改造型要重新渲染
02

TYPE 2 · 2.5D 场景

把现场画成一张好读的图。

2.5D 不是简化版 3D，是更偏信息表达的空间设计。

  • 产线
  • 车间
  • 堆场
  • 约 2–4 周

2.5D 场景 · 01

从设备到 2.5D：先理解，再概括。

先搞懂设备是干什么的、哪部分在动，再用统一的画法把它「翻译」成图形。

→→

2.5D 场景 · 02

设计语言：四条规则，所有看板通用。

统一视角固定等轴角度，所有设备同一个方向
统一比例设备大小按真实比例，方便对照现场
运行待机故障停机
状态色专用设备本体用冷灰，颜色只留给状态
标签贴近设备文字水平摆放，引线指向设备
  1. 定需求谁看、看什么、做什么判断
  2. 排布局按工艺顺序分区
  3. 画设备做成可复用的组件Figma
  4. 拼场景组件拼成产线、堆场Figma
  5. 标状态颜色 + 图标 + 文字
  6. 加动效只动正在变化的地方

2.5D 场景 · 03

一套组件，拼出五条产线。

设备画一次，换个排列就是新产线；信息位置不变，看过一块就会看下一块。

2.5D 场景 · 04

加动效：只动正在变化的地方。

设备工作有轻微动作，异常才闪烁，其他区域保持安静。

2.5D 场景 · 05

交给开发：底图 + 图层 + 坐标。

分层切图场景底图一层，每台设备单独一层
状态图层每台设备备好运行、待机、故障、停机四张图
坐标表标签、设备按坐标定位，开发按编号绑定数据
动效序列帧或 CSS 动画，只对指定设备播放
遇到的问题原因怎么解决
设备太多，画不完每条产线几十台设备做设备组件库同类设备复用
标签互相遮挡设备密集错开引线只常显重点点开看详情
颜色看混了图例色和状态色撞色状态色专用图例换形状
新产线要上工艺不同同一套组件拼装信息位置不变
03

TYPE 3 · 3D 数字孪生

把真实园区搬进屏幕。

从无人机航拍开始，到引擎里跑起来，设计和开发要一路配合。

  • 园区
  • 工厂
  • 城市
  • 约 1–3 个月

3D · 01

整体流程：七步，前四步在设计。

  1. 航拍采集无人机按航线拍，配 CAD 总图设计
  2. 建模厂房、道路、重点设备C4D · Blender
  3. 减面只留看得见的外壳Blender
  4. 贴图烘焙光照烘进贴图，省性能Blender
  5. 导出FBX / GLB，统一命名和单位设计 → 开发
  6. 引擎搭建场景、镜头、交互Unity / Three.js
  7. 接数据上屏接口绑定、打包运行开发

3D · 02

建模：只做看得见的。

屏幕上看不到的面，一个都不要。模型越轻，现场越流畅。

剪掉内部厂房只留外壳，看不到的结构全删
远近分级远处用简模，镜头靠近再换精模
重复设备只做一个同型号设备复用一份模型
细节交给贴图螺栓、纹理画在贴图上，不建几何体

面数变化 · 示意

原始模型100%
删除内部结构45%
合并、减面18%
远景简模6%

数值为示意，实际按场景大小和主机性能定目标。

3D · 03

过程中会遇到的问题。

卡、慢、糊、对不上，几乎每个 3D 项目都会碰到。提前想好办法。

遇到的问题原因怎么解决
场景卡顿、掉帧面数高、贴图大、物体多减面远近分级合并模型光照烘焙
第一次打开很慢模型包太大分区按需加载压缩贴图先显示总览
动效一多就卡粒子、透明叠加太多用贴图流动代替粒子只动重点设备
数据和模型对不上命名不统一模型名 = 设备编码维护一张对照表
拼接屏上字发糊分辨率不匹配按拼接总分辨率设计界面不随场景缩放
放到网页里跑不动模型包体大、引擎选得不对大屏用应用运行网页另做轻量版GLB 压缩

3D · 04

交给开发：设计要交什么，开发要做什么。

设计这一侧交的不只是模型，还有命名、贴图、镜头和字段表；开发在引擎里把它们和数据连起来。

设计交什么格式和要求开发拿去做什么
模型FBX 或 GLB（见下表），单位、朝向统一；每个设备一个独立物体导入引擎，作为可点击、可变色的对象
命名与对照表模型名 = 设备编码，再附一张「编码 ↔ 设备 ↔ 区域」表数据按编码挂到对应模型，不靠人工对
贴图与材质合并贴图集，限制尺寸；自发光单独一张减少内存和绘制次数，保证大屏上不卡
烘焙光照静态光影烘焙进贴图，只留少量实时光画面有质感，同时不占算力
镜头路线关键机位、停留时长、过渡方式，写成脚本表开发按表做镜头飞行，总览 → 车间 → 设备
界面与动效界面切图和规范、动效时长与曲线，按拼接分辨率出稿界面叠在场景上，动效按规范还原
数据字段表每块面板要什么数据、单位、刷新频率、异常怎么显示对接口、做兜底（没数据、数据异常）

数据来源

  • 人员定位、门禁

3D · 05

用 Unity，还是 Three.js？

数字孪生的引擎不止一种，选哪个看放在哪里、给谁看。没有绝对的好坏，只有合不合适。

Unity：大屏、展厅、指挥中心

  • 画质高，光照、后处理、粒子都好做
  • 场景大、模型精细也能跑，适合园区、工厂整体孪生
  • 镜头飞行、动画有成熟工具（Timeline、Cinemachine）
  • 打包成应用，在固定的大屏主机上运行
  • 代价：要会 C#，包体大，网页里不方便直接打开

Three.js：网页端、轻量查看

  • 浏览器里直接打开，发个链接就能看
  • 前端熟悉，和现有页面、接口、权限天然在一起
  • 适合设备较少、模型轻量、交互简单的场景
  • 代价：画质和性能有上限，场景一大就吃力，特效要自己写
场景特点建议
大屏要求流畅、画质高场景大、模型精细、特效多打包成应用（Unity 等引擎）：不卡，画质最好，但开发门槛高，要懂引擎
大屏直接打开网页想快速改、随时更新，多块屏共用一个地址网页引擎（Three.js 等）：开发快、好维护；场景一大、特效一多，就容易卡
大屏之外，手机、电脑也要看设备性能差别大，要打开就能用网页端做精简版：减面、压缩、少特效；大屏用完整版
场景很大，又必须走网页模型多、面数高，网页扛不住考虑云渲染：画面在服务器上跑，视频流推到浏览器

导出格式

模型带动画，交 FBX 还是 GLB？

先定引擎，再定格式：Unity 多用 FBX，网页引擎多用 GLB。

格式用在哪里动画怎么带
FBXUnity、Unreal 的首选；C4D、Blender 都能直接导出支持关键帧动画、骨骼动画，导出时勾选「烘焙动画」；一个文件可以带多段动画
GLB（glTF 2.0）Three.js、Babylon.js 等网页引擎的首选；一个文件打包模型、贴图、动画支持关键帧、骨骼、形变动画；可用 Draco 压缩，体积小、加载快
OBJ只有模型和简单材质不带动画，只适合静态场景或临时预览
贴图视频 / 序列帧屏幕内容、水流、光带这类效果不做成模型动画，直接用贴图滚动或视频贴图，省性能
  1. 动画分段每段动画单独命名，比如「开门」「运转」「报警」，开发按名字调用
  2. 烘焙关键帧约束、表达式、动力学在引擎里不认，导出前烘焙成关键帧
  3. 只动该动的动画挂在设备的活动部件上，不整体动，方便单独控制
  4. 导出后验证用 Blender 或在线 glTF 查看器打开，确认动画、贴图、比例都对
